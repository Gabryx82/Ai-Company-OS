# TASK-002 — Implementazione

## Forma del modulo

Il modulo `project` segue la struttura già usata da `agent` e `task`, con due cartelle in
più che quelle non avevano bisogno:

```
com.aicompany.backend.project
├── model
│   ├── Project.java          entità + regole di ciclo di vita
│   └── ProjectStatus.java    insieme chiuso ACTIVE / ARCHIVED
├── repository/ProjectRepository.java
├── service/ProjectService.java
├── dto
│   ├── ProjectCreateRequest.java
│   ├── ProjectUpdateRequest.java
│   └── ProjectResponse.java
├── controller
│   ├── ProjectController.java
│   └── ProjectExceptionHandler.java   advice limitato a questo controller
└── exception
    ├── ProjectNotFoundException.java
    ├── ProjectNameAlreadyExistsException.java
    └── IllegalProjectStateTransitionException.java
```

## 1. Lo schema

`backend/src/main/resources/db/migration/V2__create_projects.sql`

```sql
CREATE TABLE projects (
    id          BIGINT                   GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name        VARCHAR(120)             NOT NULL,
    description VARCHAR(2000),
    status      VARCHAR(32)              NOT NULL,
    created_at  TIMESTAMP WITH TIME ZONE NOT NULL,
    updated_at  TIMESTAMP WITH TIME ZONE NOT NULL,
    CONSTRAINT projects_status_check CHECK (status IN ('ACTIVE', 'ARCHIVED'))
);

CREATE UNIQUE INDEX projects_name_unique_idx ON projects (lower(name));
CREATE INDEX projects_status_idx ON projects (status);
```

Tre cose meritano una nota.

**La migrazione è additiva.** Non tocca `agents` né `tasks`, non aggiunge chiavi esterne. È
la ragione per cui applicarla su un database già popolato non ha rischi: crea una tabella e
due indici, nient'altro. Verificato sul volume di sviluppo reale.

**Il check constraint non è ridondante con l'enum.** L'enum protegge il percorso
applicativo. Il constraint protegge tutto il resto: import, script di manutenzione,
correzioni fatte a mano in `psql`. Senza di esso una `UPDATE projects SET status = 'DELETED'`
passa, e il fallimento arriva alla lettura successiva — lontano dalla causa e senza indicare
chi l'ha scritto.

**L'unicità del nome è funzionale su `lower(name)`.** Un registro in cui coesistono
«Company OS» e «company os» è rotto qualunque sia quello giusto.

## 2. L'entità possiede il proprio ciclo di vita

`Project` non espone un setter per `status`. Un chiamante chiede una transizione, e l'entità
decide se è legale:

```java
public void archive() {
    requireStatus(ProjectStatus.ACTIVE, ProjectStatus.ARCHIVED);
    this.status = ProjectStatus.ARCHIVED;
}

private void requireStatus(ProjectStatus expected, ProjectStatus target) {
    if (status != expected) {
        throw new IllegalProjectStateTransitionException(status, target);
    }
}
```

Se la regola stesse nel service, ogni nuovo punto d'ingresso — un'altra API, un importer, un
agente automatico — dovrebbe ricordarsi di riapplicarla. Qui è impossibile aggirarla.

`ProjectLifecycleTest` verifica queste proprietà senza Spring e senza database: sono
proprietà dell'oggetto di dominio, non della persistenza, e testarle in isolamento le rende
leggibili e istantanee.

## 3. Il contratto HTTP

| Metodo | Path | Esito |
|---|---|---|
| `POST` | `/api/projects` | `201` + `Location`, nasce `ACTIVE` · `400` · `409` |
| `GET` | `/api/projects` | `200`; filtro opzionale `?status=ACTIVE\|ARCHIVED` · `400` se il valore non esiste |
| `GET` | `/api/projects/{id}` | `200` · `404` |
| `PUT` | `/api/projects/{id}` | `200` · `400` · `404` · `409` |
| `POST` | `/api/projects/{id}/archive` | `200` · `404` · `409` se già archiviato |
| `POST` | `/api/projects/{id}/restore` | `200` · `404` · `409` se già attivo |
| `DELETE` | `/api/projects/{id}` | **`405`** — non esiste cancellazione fisica |

`GET /api/projects` senza parametri restituisce **tutto**, archiviati compresi. La
tentazione era nascondere gli archiviati per default, ma un filtro implicito in un endpoint
di elenco è il tipo di comportamento che si scopre mesi dopo, quando un conteggio non torna.
Il filtro esiste ed è esplicito.

I DTO di ingresso non hanno né `id` né `status`: un client non può scegliere
l'identificatore né creare un progetto già archiviato. `ProjectUpdateRequest` è una
sostituzione completa dei campi descrittivi, non una patch — un `description` assente lo
azzera.

## 4. Unicità: due controlli, un contratto

```java
public Project create(String name, String description) {
    if (repository.existsByNameIgnoreCase(name)) {
        throw new ProjectNameAlreadyExistsException(name);
    }
    return saveGuardingUniqueName(new Project(name, description), name);
}
```

Il controllo `exists` produce il `409` leggibile nel caso ordinario. Non è una garanzia: due
richieste concorrenti possono superarlo entrambe. L'indice unico è ciò che effettivamente
impedisce il duplicato, e `saveGuardingUniqueName` traduce la
`DataIntegrityViolationException` risultante nella stessa eccezione, così l'API risponde
`409` in entrambi i percorsi.

`saveAndFlush` invece di `save` è necessario: senza il flush la violazione emergerebbe al
commit della transazione, cioè **dopo** che l'advice ha già costruito la risposta, e
diventerebbe un `500`.

## 5. Perché l'advice è limitato a un controller

```java
@RestControllerAdvice(assignableTypes = ProjectController.class)
class ProjectExceptionHandler { ... }
```

Un advice globale avrebbe cambiato le risposte che `agents` e `tasks` già producono: un
cambio di contratto osservabile su API preesistenti, fuori dallo scope. Il prezzo è che per
un periodo l'API ha due forme di errore — `ProblemDetail` sotto `/api/projects`, il default
di Spring altrove. È una disomogeneità nota, coperta dal test
`theProjectErrorContractDoesNotLeakIntoTheTaskApi`, e si chiude quando si affronta TD-07.

Il gestore di `MethodArgumentTypeMismatchException` non è decorativo: senza di esso
`?status=DELETED` fallisce durante il binding del parametro e diventa un `500`.

## 6. Timestamp

`Instant` su colonne `TIMESTAMP WITH TIME ZONE`, valorizzati da `@PrePersist` / `@PreUpdate`.

Su una colonna senza fuso l'offset si perderebbe in silenzio: il valore riletto resta
plausibile ed è sbagliato. `validate` di Hibernate non è affidabile su questa distinzione,
quindi il tipo della colonna è asserito da un test
(`projectTimestampsAreStoredWithATimeZone`).

Valorizzarli dall'entità invece che con `DEFAULT now()` fa sì che l'oggetto in memoria
coincida con la riga subito dopo il salvataggio, senza un giro di lettura. Il compromesso è
che l'orologio è quello dell'applicazione: con più istanze non sincronizzate l'ordinamento
per `created_at` può essere leggermente incoerente. Irrilevante con un processo solo, da
rivedere prima di scalare.

## 7. Effetto collaterale obbligato: la fixture `V2` dei test

`src/test/resources/db/fixture/v2/V2__task_001a_probe.sql` rappresentava «la prossima
migrazione di schema» nei test di TASK-001A. Con una `V2` reale nello stream, Flyway avrebbe
trovato due migrazioni con la stessa versione e fallito.

La fixture diventa `db/fixture/next/V900__probe_next_schema_migration.sql`. Il numero è
vincolato da entrambi i lati, ed è scritto nella fixture stessa:

- **sopra** la testa di `db/migration`, o collide con una migrazione reale;
- **sotto** `1000`, o la fixture legacy non riesce più a riprodurre il fallimento R1 —
  che richiede una storia di schema più avanti delle migrazioni risolte.

Per non ripetere il problema alla prossima migrazione, le asserzioni che elencavano a mano le
versioni applicate ora le leggono da Flyway:

```java
private static List<String> resolvedSchemaVersions() {
    return Arrays.stream(Flyway.configure()
                    .dataSource(dataSource())
                    .locations(SCHEMA_LOCATION)
                    .load().info().all())
            .map(info -> info.getVersion().getVersion())
            .toList();
}
```

`SchemaMigrationTest` e `DevSeedMigrationTest` conservano invece l'elenco esplicito
`("1", "2")`: lì l'asserzione è deliberatamente rigida, perché il punto è che **nessuna
versione di seed** finisca nella storia di schema. Una futura migrazione le farà fallire, ed
è il comportamento voluto: chi aggiunge una `V3` deve dichiararla anche lì.

## Cosa non è stato fatto, e perché

| Non fatto | Ragione |
|---|---|
| `Task.project_id` | Richiede tre decisioni di dominio non prese e una migrazione su tabella popolata (ADR-004 §1) |
| Slug pubblico | Il nome è oggi la chiave naturale; uno slug immutabile serve quando serviranno URL stabili |
| Paginazione di `GET /api/projects` | Nessun volume che la giustifichi; aggiungerla dopo cambia il contratto, è un debito consapevole |
| Contratto di errore uniforme su tutta l'API | TD-07, decisione a sé |
| Enum su `Task.status` / `priority` | Fuori scope |
